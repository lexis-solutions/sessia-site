Context switching without the fatigue.

Switching is not what wears you out. Hunting for the right window is, and re-reading a wall of text, and keeping in your head what you left unfinished. Sessia takes those off you:

  • One page shows which Claude Code session needs you.
  • Answers come back in the same structure.
  • What you would have to remember is written down.

Sessia is a dashboard for Claude Code with a worked-out way for every step of the development cycle, from knowing which session needs you to the reviewed merge request and the word “ship”, so a lot of it becomes frictionless and your attention stays on the decisions.

Start Claude Code the way you always do. Sessia finds every session running on your machine, however you started it. It runs there too, with no account.

1 · See every session

Know which session needs you

  • One page for every Claude Code session running on your machine, grouped by project.
  • Each shows its name and its status: working, waiting for you or idle, and for how long. Often that is enough.
  • A waiting one says what it waits for: a question it asked, or a permission it needs.
  • Open jumps to its VS Code window and tab.
  • A notification with a sound when one needs you, so you are told when you are needed and react when you want.

Run two or three sessions, or as many as your machine can handle. Thinking at that speed is still work, so the pace is yours.

2 · Pick up, and decide

Read where a session stands in seconds

You read the last message of each turn, so that message holds everything, in the same order every time. Ideas and choices come as numbered questions with lettered options, the one recommended and why, so you answer in one line.

Without the structure: the same answer, as it usually comes

I looked into the export timeout. At first I thought the server was running out of memory, but after going through the logs it turned out the problem was in our code: the export ran one database query per invoice, so with a few thousand invoices it hit the timeout. I've rewritten it to run a single query for all invoices, and it now takes about 4 seconds. I pushed the branch and opened merge request #41, so you can take a look when you have a moment. One thing I noticed along the way: the old export also included cancelled invoices, probably by accident, but the accountants may rely on it. I'd lean towards leaving them out, since nobody can pay them and it matches what the invoice list shows, but I can keep them in as before if you prefer. Let me know which way you want to go.

  1. 1The 📌 label names the tab and the session's card, so many tabs read as many different jobs.
  2. 2The verdict line says at a glance whether the session is finished.
  3. 3In short is the whole state in a few lines, what needs you at the top, with at most three lines under it.
  4. 4A decision carries its background, lettered options and a pick, so you can answer it without having followed the session: “1 B”.
  5. 5A correction is named as one, so nothing you were told earlier stays wrong.
  6. 6Bugs lists every bug the session logged, worked on or fixed, and where each one stands.
  7. 7Branches lists each branch with its merge request and the commands to try it, so nothing is left to find.

In daily use the structure has been extremely stable: a hook sends an answer that breaks it back to the session, up to three times, and one still broken after that comes with a warning you see.

3 · The merge request is ready

Reviewed before you open it

  1. Pushes the branch when it is ready.
  2. Opens the merge request on GitHub, with a Summary and a Why, a Decisions part when a choice was made, and screenshots when the change shows in a browser.
  3. Has it reviewed in a fresh context, so the code is not graded by the session that wrote it. The review goes on it as a comment.
  4. Hands it to you to read. Read Decisions closely: it is where a session could have gone the wrong way.

This is asked of every session in its rules. No hook checks it.

4 · You say “ship”

The decision stays yours

  • You type “ship” once you have read it. The session merges, deploys by the repo's own steps, checks that production answers, and cleans up the branch and its folder.
  • Until you type “ship” or “deploy”, a hook refuses the merge and the commands that change a production server.
  • It reads your own latest message, so a pasted prompt or a subagent cannot open it.

The hook is a word list: it catches slips, not everything. The deploy steps are each repo's own.

5 · Bugs and to-dos are kept

What a session finds on the way is written down

  • Bugs into BUGS.md, to-dos into TODO.md, each with a priority.
  • Pushed at once, and the session goes back to your task.
  • Shown as boards, high priority at the top.
  • ▶️ Start opens a new session on an item, with its text ready to send.
  • Dated work into SCHEDULED.md: numbered, overdue in red, with a notification when it comes due.

Writing them down is asked of a session, not enforced. A scheduled item reminds you; it runs nothing.

6 · The safety net

See what could still get lost

  • Sessions that stopped mid-work stay listed until you dismiss them: after a crash, a force quit or VS Code quitting, or when they ended with tasks still open.
  • Code not safe yet lists, in every repo, uncommitted changes, commits that exist on this machine alone, branches not merged, and main folders behind GitHub.
  • Worktrees are how it works: each branch gets its own folder, so sessions in the same repo don't step on each other's changes.
  • A worktree is deleted after checks: nothing uncommitted, no commit on this machine alone, and no session running there or stopped mid-work there.
  • A hook refuses a commit on the main branch when a Claude session runs git; your own commit passes.

Why you can trust it

It runs on your machine

No account to make, and no server of ours that your sessions pass through.

  • Local: it runs at localhost, and reads the files Claude Code and git already keep.
  • What it asks outside: through your own gh login it reads merge requests and commit authors' pictures from GitHub, and for a GitLab repo it sends a commit e-mail to a picture service.
  • Tested on throwaway repos: checks of the page's logic, a test in a real browser, and a test for each hook.

The plain limits

  • Claude Code, macOS and GitHub today, and VS Code for the Open and Start buttons.
  • It reads the sessions of VS Code and the terminal. Other ways of running Claude Code are untried.
  • It reads Claude Code's own files, which are not a documented interface, so a Claude Code release can break it.
  • Lists can be up to 30 seconds behind.

How it grows

A rulebook that grows from use

You no longer explain the same thing to every session.

  • Each rule came from something that went wrong or got in the way, and carries its date and its reason.
  • /add-rule turns a sentence into a rule and puts it live.
  • Facts go into the repo, not into one machine's memory, so a colleague's sessions know what yours know, and the facts can be reviewed like code.
  • A session that ended on a finished report leaves the list by itself, so what is listed is still open, and an empty page means you are done.

Install

Install, and what it needs

Sessia is not public yet, so the install command comes with the release.

cd ~/Projects

cd sessia && ./setup.sh
  • setup.sh switches on the hooks and the skills for every folder inside Sessia's folder, and starts the page at login, at http://localhost:7357. Running it again changes nothing.
  • Your projects go inside Sessia's folder, or stay where they are with ./setup.sh root-dir=~/code. Sessions elsewhere still show, under Other.
  • The page also works on its own: python3 dashboard.py in Sessia's folder starts it, with no setup. The rules and the hooks are what give the answers their structure.

What it needs

  • macOS, Python 3, Claude Code, git 2.55 or later (for its config-based hooks) and jq.
  • VS Code, for the Open and Start buttons.
  • gh, logged in, for merge requests.
What setup.sh changes, and how to undo it

Each change, with the command that takes it back, for Sessia in ~/Projects/sessia. If you named another projects folder with root-dir, put that folder in place of ~/Projects/sessia in the git hooks' line and in Claude's memory line. Everything else it writes stays inside Sessia's folder.

The page starts at login
A login item in ~/Library/LaunchAgents/ starts the page and starts it again if it stops, with a log in ~/Library/Logs/. The first line finds it by what it runs. 
P=$(grep -lF "$HOME/Projects/sessia/dashboard.py" ~/Library/LaunchAgents/*.plist)
launchctl bootout gui/$(id -u) "$P"
rm "$(plutil -extract StandardErrorPath raw "$P")" "$P"
The git hooks
One line in ~/.gitconfig switches them on for every repo inside Sessia's folder, and nowhere else. 
git config --global --unset "includeIf.gitdir:$HOME/Projects/sessia/.path"
The Claude Code hooks
Six hooks in ~/.claude/settings.json. Each does nothing in sessions outside Sessia's folder. 
jq --arg p "$HOME/Projects/sessia/" '.hooks |= (map_values(map(.hooks |= map(select(.command // "" | startswith($p) | not)) | select(.hooks | length > 0))) | with_entries(select(.value | length > 0)))' ~/.claude/settings.json > /tmp/settings.json && mv /tmp/settings.json ~/.claude/settings.json
Transcripts kept 90 days
Claude Code keeps them 30 by default; setup.sh sets 90 in ~/.claude/settings.json only when you had set nothing. 
jq 'del(.cleanupPeriodDays)' ~/.claude/settings.json > /tmp/settings.json && mv /tmp/settings.json ~/.claude/settings.json
The skills
Links in ~/.claude/skills/ to /add-rule, /review-mr and /move-in. 
find ~/.claude/skills -maxdepth 1 -type l -lname "$HOME/Projects/sessia/.claude/skills/*" -delete
The model-advice mod
A Claude Code plugin, from Sessia's own plugin source, that suggests a cheaper or stronger model before a message is sent. 
claude plugin uninstall model-advice@sessia
claude plugin marketplace remove sessia
Claude's own memory off
Each repo in Sessia's folder gets "autoMemoryEnabled": false in its .claude/settings.local.json, which git there ignores. 
find ~/Projects/sessia -maxdepth 4 -path '*/.claude/settings.local.json' -not -path '*/.worktrees/*' -exec sh -c 'jq "del(.autoMemoryEnabled)" "$1" > "$1.tmp" && mv "$1.tmp" "$1"' _ {} \;
A projects folder named with root-dir
Links in that folder to Sessia's rules and hooks, and the folder's name in Sessia's own git settings. For ~/code: 
rm ~/code/CLAUDE.md ~/code/.claude/on-demand ~/code/.claude/hooks
git -C ~/Projects/sessia config --unset sessia.root

FAQ

Questions people ask

Do I have to move my projects into Sessia's folder?

No. ./setup.sh root-dir=~/code makes your own folder the projects folder: it links Sessia's rules and hooks into it, and stops if the folder already has a CLAUDE.md of its own. Its folders then make the page's menu, and the page can change the folder later.

Does it change Claude Code, or my own CLAUDE.md files?

Claude Code itself and your repos' own CLAUDE.md files stay as they are. Sessia's rules are a CLAUDE.md in the projects folder, which Claude Code reads above each project's own. The main changes setup.sh makes, to Claude Code's settings among them, are listed under Install, with how to undo them.

Does it cost tokens?

Sessia itself costs nothing. Its rules are about 37 KB of text that each session re-reads on every turn, and a cheap model, Haiku, checks some answers, so they add some tokens. They also ask for short conversations and cheaper models for easy work, and on one person's use a model call then cost about 40% less (Cost).

Can I use it with colleagues?

Today each person runs Sessia on their own machine, for their own sessions, and there is no shared view. The facts and rules live in the repos, so a colleague's sessions know what yours know. Using it together is something we are thinking about.

Does it run on Windows?

The page does, started by hand with start-sessia.cmd, but setup.sh, the hooks and the start at login are macOS only. If you use it on Windows, open pull requests: help in that direction is welcome, and we will extend it quickly. Some of that work is planned on a Windows machine of our own.

Can I try it without changing my setup?

Yes. The live copy at the top is the page with made-up sessions. In a clone, python3 demo.py . 7399 runs it on made-up sessions at localhost:7399, and python3 dashboard.py starts it on your own sessions, with no setup.

Can I change the rules?

Yes. /add-rule turns a sentence into a rule and puts it live, or you edit them yourself: they are plain Markdown in Sessia's folder. Fork it if your way differs.
